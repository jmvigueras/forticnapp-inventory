[^27]: **How a count is measured, and where that lives.** Counts are reported with the window they cover and the instrument that produced it, decided per resource type and per account: the scripts probe for the best instrument available and fall back when it is absent, always labelling which path was taken. The instruments are AWS Cost Explorer (metered instance-hours recovered to a count), AWS Config (existence history), GCP Cloud Asset Inventory at a past `read_time`, and a point-in-time enumeration as the floor.

    **The instrument-specific mappings deliberately do not live in this document.** Cost Explorer speaks *usage types* (`USW2-BoxUsage:m5.large`) and AWS Config speaks its own resource-type identifiers (`AWS::RDS::DBInstance`); both are implementation details of one instrument on one cloud, with no counterpart on the other two — Azure Cost Management's strings differ entirely and GCP has no equivalent tier. A column here that was blank for two of three CSPs would be noise. They live in the scripts instead, as `CE_USAGE_RULES` and `CONFIG_TYPE_RULES` in `count_aws_resources.py`, each documented in place with why a given resource type is or is not included.

    **What this document governs is what is counted; the ladder only governs how well it can be measured over time.** No resource type's definition changes with the instrument. Where an instrument cannot reproduce a counting rule in this document, it declines and the next one is used — it never approximates the definition.

[^1]: **VM — Container Host merge:** The former "Container Host" category has been merged into VM and removed from this mapping. FortiCNAPP does not bill for Kubernetes/ECS orchestration constructs, so cluster, node group, agent pool, and node pool resource types are excluded entirely — this removes `microsoft.containerservice/managedclusters` (AKS), `eks:cluster`, `eks:nodegroup`, `ecs:cluster`, `container.googleapis.com/Cluster` (GKE), and `container.googleapis.com/NodePool` from the mapping with no replacement. `ecs:task-definition` is also excluded — it is a versioned blueprint, and a family can carry fifty revisions with nothing running from any of them, so counting it measures recipes written rather than workload deployed. **`ecs:service` is no longer excluded** — ruled 2026-09-17, reversing `38b4aee`; the reasoning is in [^3]. `eks:fargate-profile` and `ecs:service` are the exceptions that move to Serverless Container rather than being dropped, since Fargate is a real, billable compute engine even though it has no discrete node (see [^3]).

[^2]: **VM — completeness:** AWS `ec2:instance` and GCP `compute.googleapis.com/Instance` already capture instances launched via Auto Scaling Groups / Managed Instance Groups directly (queried by instance, not by group membership), so ASG/MIG-launched instances — including EKS and GKE node instances — are captured with no additional query logic. `lightsail:instance` added for AWS: a real compute instance outside the `ec2:` namespace that was previously uncounted. Azure `microsoft.compute/virtualmachinescalesets/virtualmachines` added to close a genuine completeness gap: AKS nodes are backed by VM Scale Sets, which carry a distinct resource type from standalone VMs and were not counted anywhere in the previous mapping (Azure, unlike AWS/GCP, keeps scale-set instances in a separate resource-type namespace from standalone VMs). **Note:** adding the type to this mapping was not sufficient to actually close that gap — see [^17] for why it kept returning zero until the query was pointed at the right Resource Graph table.

[^3]: **Serverless Container (AWS) — this category counts the supervisor layer on every CSP.** Ruled 2026-09-17 (finding 13). Each of these services exposes up to three layers — a blueprint, a supervisor that maintains a desired number of copies, and the running copies themselves — and **the count is taken at the supervisor layer throughout**:

    | Layer | ECS | App Runner | Cloud Run | Container Apps | ACI |
    |---|---|---|---|---|---|
    | Blueprint | `ecs:task-definition` | — | revision config | revision | — |
    | **Supervisor — counted** | **`ecs:service`** | **`apprunner:service`** | **`run.googleapis.com/Service`** | **`microsoft.app/containerapps`** | — |
    | Running copy | `ecs:task` | not exposed | not exposed | not exposed | **`containergroups`** |

    **Why this changed.** `38b4aee` swapped `ecs:service` for `ecs:task`, on the grounds that a service is "a desired-state/scaling construct, not a deployed resource." That argument cannot be applied consistently: a Cloud Run Service and a Container App are *also* desired-state constructs — a declared revision plus scaling bounds, with the platform running N hidden instances — and both are counted. Enforced everywhere, the rule would empty this row on two of three CSPs; enforced only against AWS, it left one ECS service on fifty Fargate tasks counting **50** where the identical workload on Cloud Run counts **1**. The original exclusion was in any case an artifact of the Container Host merge (`ecs:service` was dropped as "not a node", alongside `eks:cluster` and `ecs:cluster`), and the later choice between `ecs:task-definition` and `ecs:task` was a two-way pick between a blueprint and a replica made *after* the supervisor layer had already been removed from the field. ECS is simply the only service here that exposes all three layers, so API granularity — not the deliverable — decided the unit. **Consequence: this row's magnitude falls for ECS-heavy AWS customers**, which matters to whoever owns the 10:1 ratio in [^24], since that ratio was set while AWS counted replicas.

    **`ecs:service` is filtered to ACTIVE Fargate services, and the launch-type filter is deliberately not used.** `ListServices` offers a server-side `launchType` filter, but `Service.launchType` is documented as **omitted when the service was created with a capacity provider strategy** — the console's modern default — so that filter returns a clean, wrong answer, exactly the failure shape as the VMSS table bug in [^17]. Implementation therefore lists all services and calls `DescribeServices` (batches of 10), treating a service as Fargate if `launchType == FARGATE` **or** its `capacityProviderStrategy` names `FARGATE`/`FARGATE_SPOT`. EC2-launched services are excluded: they run on EC2 instances already counted under VM, the same reasoning that keeps K8s pods from being counted separately from their already-counted nodes.

    **Unsupervised Fargate tasks are counted too, as their own resource type `ecs:standalone-task`.** A task started by `RunTask` or a scheduled rule — a batch job, a migration, a cron task — has no service above it, so at supervisor granularity the task *is* the workload and would otherwise vanish. **It was split out of `ecs:service` on 2026-09-18** (previously both were summed under `ecs:service`). The category total is unchanged; what changes is that the two halves are now visible separately and can be measured by different instruments. That is the practical reason for the split: `AWS::ECS::Service` is an AWS Config resource type and a bare ECS task is not, so while they shared one resource type the whole row was pinned to a point-in-time count — the alternative being to blend a smoothed service count with a snapshot task count inside a single number. ECS names the task group `service:<name>` when a service owns the task and `family:<name>` otherwise, so `DescribeTasks` (batches of 100) separates them; service-owned tasks are skipped as replicas of an already-counted service. Fargate-ness is decided by the same two-field test, since `Task` carries `capacityProviderName` alongside `launchType`. `ListTasks` still defaults to `desiredStatus=RUNNING`, so tasks still provisioning are included (see the tool-divergence note in the live-verification queue).

    **`eks:fargate-profile` is kept, but it is not a workload** (finding 12, ruled 2026-09-17). A Fargate profile is a **pod routing rule** — namespace and label selectors saying which pods run on Fargate instead of on a node. It contains no image and no workload, and one profile can match zero pods forever or route thousands. It is bounded at **10 profiles per cluster** (adjustable) with 5 selectors each, and is typically 1–2, so at 10:1 it contributes roughly 0.1–0.2 billable resources per cluster in either direction. It is kept as a **bounded presence indicator** rather than dropped, because dropping it turns Fargate-on-EKS into a silent zero and a visible imperfect number beats an absent one. The only real fix is counting Kubernetes Deployments through the Kubernetes API, which AWS APIs cannot reach. That is data-plane access, and it is ruled out: the scripts are control-plane only (2026-09-25, OI-1).

    **Container jobs count once per job** (ruled 2026-09-25, OI-3): `run.googleapis.com/Job` on GCP and `microsoft.app/jobs` on Azure, both in this row. A job holds one current template and a trigger (manual, schedule or event), and each run creates an *execution* that is ephemeral. Found live in demo-beta on 2026-09-10: 5 Cloud Run Jobs against 5,148 executions. The job is counted and the execution is not, for the same reason a bucket is counted rather than its objects. The closest shape elsewhere in the mapping is a Lambda function: a defined unit of code invoked on demand, counted whether or not it is running. Executions are not Resource Graph resources on Azure in any case. **Known asymmetry:** an ECS task started by an EventBridge schedule is counted only while it runs (`ecs:standalone-task`), because AWS has no job-definition resource on the ECS side to count instead.

    **`lightsail:container-service` is counted at the supervisor layer** (ruled 2026-09-25, OI-4). A Lightsail container service runs `scale` nodes (1 to 20) of a fixed `power` and holds its deployments as nested objects, so the service is the supervisor and is counted once.

[^4]: **Serverless Container (Azure):** Azure Container Instances (`microsoft.containerinstance/containergroups`) is documented by Microsoft as a serverless on-demand container execution service and belongs here alongside Container Apps. It was absent from the previous mapping.

[^5]: **Container Image:** AWS and GCP count at individual image granularity; Azure counts at registry granularity, which will undercount relative to AWS and GCP. AWS (`ecr:image`) excludes manifest list entries (multi-arch index manifests). GCP (`artifactregistry.googleapis.com/DockerImage`) counts only Docker images — non-Docker artifact types (npm, Maven, Python packages) stored in Artifact Registry are excluded. GCR (`gcr.io`) images are covered: Google migrated Container Registry to be backed by Artifact Registry in 2023, so images pushed via gcr.io surface as `artifactregistry.googleapis.com/DockerImage` and are included in the count. Azure (`microsoft.containerregistry/registries`) counts registries, not images or repositories; per-image counts would require the registry's data-plane API, which is not available via Resource Graph. **Control plane only, ruled 2026-09-25 (OI-1):** the scripts read only what the managed read-only roles expose (`ReadOnlyAccess`, `Reader`, `cloudasset.viewer`) and never use data-plane access. Listing ACR images would need registry data roles (`AcrPull`, or `Container Registry Repository Reader` plus `Repository Catalog Lister`) that can also pull the images, i.e. read the customer's software, and `Reader` does not grant them. **This undercount is therefore accepted permanently, not pending.** At this row's 300:1 ratio its billing effect is small: a registry holding 900 images is 3 billable units against 0.003 counted. GCP Artifact/Container Registry *repositories* (as opposed to the images within them) are deliberately not added here — counting repositories would double-count against the image-level `DockerImage` count already in this row.

    **Images in on-prem registries count here too** (ruled 2026-10-20). The proxy scanner assesses images in self-hosted registries such as Harbor and Nexus, which no cloud API can see, so the customer supplies the image count and it is added to this row, at 300:1, alongside any cloud images. Like the on-prem host rule in [^13], this is a customer-supplied figure and belongs in the sizing, not in the scripts.

[^6]: **Serverless Function (Azure):** `microsoft.web/sites` covers both App Service web apps and Function Apps — a `kind` filter is needed at query time to isolate Function Apps specifically. `microsoft.logic/workflows` (Logic Apps) and AWS `stepfunctions:statemachine` (Step Functions) were present in the previous mapping under this category but are workflow orchestration services, not serverless functions, and have been removed.

[^7]: **Managed DB (PaaS):** `elasticache:replication-group` added for AWS to cover Redis/Valkey cluster mode (previously only `elasticache:cachecluster` was listed). GCP Cloud Bigtable uses asset type `bigtableadmin.googleapis.com/Instance` (not `bigtable.googleapis.com/Instance`). Azure includes both flexible-server and legacy single-server tiers for MySQL (`microsoft.dbformysql/servers`) and PostgreSQL (`microsoft.dbforpostgresql/servers`). Neptune (`neptune:db-cluster`), OpenSearch (`opensearch:domain`), DocumentDB (`docdb:cluster`), MemoryDB (`memorydb:cluster`), Keyspaces (`cassandra:keyspace`), and Timestream (`timestream:database`) have been added. Neptune and OpenSearch were previously deferred pending placement confirmation — both are provisioned always-on managed database services and belong here alongside RDS and DynamoDB. MemoryDB is a durable in-memory database with its own CloudFormation resource type (`AWS::MemoryDB::Cluster`), distinct from ElastiCache. Azure SQL Managed Instance (`microsoft.sql/managedinstances`), Azure Data Explorer (`microsoft.kusto/clusters`), and Azure Database for MariaDB (`microsoft.dbformariadb/servers`) added. GCP AlloyDB (`alloydb.googleapis.com/Cluster`) and Cloud Spanner (`spanner.googleapis.com/Instance`) added — both are fully managed provisioned database services with dedicated Cloud Asset Inventory asset types.

    **Cluster/instance double-counting removed:** `docdb:db-instance`, `neptune:db-instance`, and `alloydb.googleapis.com/Instance` have been dropped. DocumentDB, Neptune, and AlloyDB instances are always members of a cluster, so counting both the cluster and its instances counts the same database twice — the same reason `rds:db` filters out instances carrying a `DBClusterIdentifier` and lets `rds:cluster` represent Aurora. A three-node cluster counts as one on all three CSPs.

    **Keyspaces system keyspaces excluded:** `cassandra:keyspace` filters out `system`, `system_schema`, `system_schema_mcs`, and `system_multiregion_info`. Keyspaces reports these in any account where the API is reachable, so an unfiltered count returns ~4 for customers who have never used the service.

    **RDS engine guard:** `rds:cluster` excludes clusters reporting `Engine` of `docdb` or `neptune`. DocumentDB and Neptune are built on the RDS control plane and their clusters can surface through `describe_db_clusters`; they are counted by `docdb:cluster` and `neptune:db-cluster` instead. **Confirmed against the AWS API reference 2026-09-10: `DescribeDBClusters` states outright that it "can also return information for Amazon Neptune DB instances and Amazon DocumentDB instances."** The guard is therefore load-bearing, not defensive — without it, every DocumentDB and Neptune cluster is counted twice, once here and once under its own type. AWS documents `engine` as a supported server-side filter value for this call, so the filter could also be pushed into the request rather than applied after the fact.

    **Added 2026-09-25 (OI-4):** Azure Cosmos DB for PostgreSQL (`microsoft.dbforpostgresql/servergroupsv2`) counts one per cluster. A cluster is a coordinator plus workers, and the nodes are properties rather than resources, the same treatment as AlloyDB and Aurora. Microsoft has the service on a retirement path with no date, but existing clusters still need counting. AWS Timestream for InfluxDB counts `timestream-influxdb:db-cluster` once per cluster, plus `timestream-influxdb:db-instance` for instances outside any cluster, the `rds:cluster` / `rds:db` split. Members are subtracted using `ListDbInstancesForCluster`, because the list API's summary carries no cluster id and the docs do not say whether members appear in it. It is a separate service from Timestream for LiveAnalytics (`timestream:database`), with its own IAM prefix. botocore's bundled endpoint data listed no regions for it at the time, so the AWS script carries a documented fallback list. **Azure SQL `master` is excluded by name** (2026-09-25, OI-14). Every logical server has a system database called `master`, and database names are unique per server, so no customer database can be named that. Whether Resource Graph returns `master` among `microsoft.sql/servers/databases` was never settled from the docs, so the exclusion is applied anyway. It is applied to the change feed too, by resource ID, and every run reports how many it removed as `sql_master_databases_excluded`. The first field run with a SQL server answers the question.

[^8]: **Data Warehouse (Azure):** `microsoft.synapse/workspaces` (Azure Synapse Analytics) replaces the incorrect `microsoft.web/sites` entry that appeared in the previous mapping. `sqladmin.googleapis.com/Instance` has been removed from this row — it belongs under Managed DB (PaaS) only. **`microsoft.fabric/capacities` is counted as a presence marker, not a warehouse count** (ruled 2026-09-25, OI-4). A Fabric capacity is a compute pool, an F-SKU that workspaces are assigned to. The warehouses and lakehouses themselves are reachable only through the Fabric REST API, a second auth path that also needs a Fabric tenant admin to allow service principals. That second path is ruled out: the scripts are control-plane only (2026-09-25, OI-1), so the capacity marker is the permanent answer, not a stopgap. Counting the capacity follows the `eks:fargate-profile` precedent in [^3]: a customer moving from Synapse to Fabric, which Microsoft publishes migration guides for, would otherwise read as a silent zero on this row, and a visible imperfect number beats that.

[^9]: **Data Warehouse (AWS):** `athena:work-group` has been removed — a workgroup is a query-execution/cost-management construct, not a warehouse resource itself, and has no counterpart at this granularity in Azure or GCP.

[^10]: **Data Warehouse (GCP):** BigQuery counts **one warehouse per (project, location) that holds at least one dataset**, not one per dataset (changed 2026-10-08). The unit priced on the other clouds is a deployment of the warehouse service — a Redshift cluster or Serverless namespace, a Synapse or Databricks workspace — each with its own storage and access boundary in one region, holding many schemas. BigQuery nests project → dataset → table, and a dataset is the schema-level namespace, one level below that: customers create them per source, per team, per environment or per export, so counting them priced how a warehouse is organised rather than how many there are. The project is where BigQuery's compute, slot reservations, quotas and billing attach, and location is a hard boundary inside it: a query runs in one location and reads only data stored there, so `US` and `europe-west2` data in one project are two warehouses, as two Redshift clusters in two regions would be. Locations are compared case-insensitively; the `US` multi-region and `us-central1` stay distinct, as they are to BigQuery. Only projects that **store** datasets count — a project that only runs queries against data held elsewhere is not a warehouse. Datasets with no readable location share one `unknown` warehouse per project and fail the `bigquery_dataset_locations_readable` canary. Hidden datasets (names starting with `_`) are not filtered; whether Cloud Asset Inventory returns them is unverified, and under this unit they can only add a location a project does not otherwise use. The ratio stays 10:1, the category's ratio, since the unit is now warehouse-level like the rest of the row. Earlier: `bigquery.googleapis.com/Table` was dropped in favour of Dataset because a per-table count had no equivalent granularity on the other two CSPs; the reason given then, that Dataset was comparable to `redshift:cluster`, did not hold.

[^11]: **Bucket Storage:** `efs:file-system` has been removed with no replacement. EFS is file-level NFS storage, conceptually distinct from the object/bucket storage this category otherwise measures (S3 buckets, Azure storage accounts, GCS buckets), and has no equivalent-granularity substitute to add in its place.

    **The operative rule for this row is count containers, not the artifacts inside them.** S3 buckets count, objects don't; Glacier vaults count, archives don't; backup vaults count, recovery points don't. This is why [^12] removing `ec2:snapshot` and `rds:db-snapshot` is *not* in tension with counting `backup:backup-vault` — a snapshot is an artifact, a vault is a container.

    **Backup containers are now counted on all three CSPs.** AWS `backup:backup-vault` was previously the only one, making the same backup estate size differently depending on cloud. Added: Azure `microsoft.recoveryservices/vaults` (Recovery Services vaults) and `microsoft.dataprotection/backupvaults` (the newer Backup vaults), and GCP `backupdr.googleapis.com/BackupVault`. **Both Azure types live in the `RecoveryServicesResources` table, not `Resources`** — querying the default table returns zero for them, the same trap described in [^17]. On GCP, only `BackupVault` is counted out of the eight `backupdr.googleapis.com/*` asset types: `Backup` is an artifact, `BackupPlan`/`BackupPlanAssociation`/`BackupPlanRevision` are policy templates, and `DataSource`/`DataSourceReference` are pointers to resources already counted elsewhere. `backupdr.googleapis.com/ManagementServer` is deliberately excluded as well — it is a deployed appliance rather than a storage container, and where it runs as a Compute Engine instance it is already counted under VM.

[^12]: **Non-OS Disk:** `ec2:snapshot` and `rds:db-snapshot` have been removed — snapshots are point-in-time backup artifacts, not persistent attached storage, and have no counterpart in the Azure or GCP entries for this row. **OS/boot disks are excluded on all three CSPs**, matching the category name: the raw resource types (`ec2:volume`, `microsoft.compute/disks`, `compute.googleapis.com/Disk`) all return every disk including root volumes, which would add roughly one phantom disk per counted VM. AWS excludes any volume whose attachment device matches its instance's `RootDeviceName`; Azure tests `properties.osType` (managed OS disks carry one, data disks do not) **and**, because a disk's `osType` says only what a disk *is* rather than whether it is currently serving a counted VM, also its `managedBy` owner and `properties.diskState` — see [^26]; GCP enumerates `compute.googleapis.com/Instance` assets first and excludes any disk appearing as a `boot: true` attachment. Unattached volumes are still counted on all three CSPs — they are provisioned storage regardless of attachment state. **This was true only of AWS and GCP until 2026-09-17:** both test *attachment* (root-device match, boot-set membership), so a detached former boot disk falls through and counts, whereas Azure's `osType` test is a property of the disk itself and silently excluded them. Corrected — see [^26]. **The boot-disk exclusion is conditional, not blanket:** it is justified by the VM line already accounting for that disk, so it lapses when the VM is not counted — see [^26].

[^13]: **Deployed Agent:** This is a FortiCNAPP billing construct based on agent installation count, not a cloud-native resource type. No CSP resource type mapping applies. **The number is determined by the customer, not discovered by the scripts** — there is nothing to query for it on any cloud, so it is entered manually alongside Developer [^25] and never appears in script output.

    **On-prem hosts count as one VM plus one Deployed Agent** (ruled 2026-10-20). FortiCNAPP has no agentless or log path on-prem: agentless workload scanning works from AWS, Azure and GCP snapshots, and the only Kubernetes audit-log integrations are EKS and GKE. So an on-prem host is seen only through its agent, and the scripts cannot see it at all. Counting it on the Deployed Agent line alone would bill it at 0.5 billable resources, against 1.5 for the same host as an agented cloud VM, although the agent does the vulnerability assessment there that the VM line pays for in the cloud. Each on-prem host, VM or bare metal, therefore adds 1 to VM and 1 to Deployed Agent. **On-prem Kubernetes follows the same rule per node:** the agent runs as a DaemonSet, one per node (control-plane nodes included where it is deployed on them), so the node count is both the VM and the Deployed Agent figure. The cluster, the compliance Cluster Collector and the running containers are not counted ([^1]). Both figures come from the customer.

[^14]: **VM Image (Azure):** `microsoft.compute/galleries/images` has been removed. In Compute Gallery, an *image definition* is a metadata container (publisher/offer/SKU, OS type, generation) holding one or more *image versions*, which are the actual replicated artifacts — counting both counts the same image twice. Versions are also the granularity that matches the other two CSPs, where an AMI and a `compute.googleapis.com/Image` are each discrete artifacts with no definition-level object above them (GCP image *families* are the nearest analogue and are likewise not counted). A version replicated to several regions remains a single Resource Graph resource, so this introduces no regional multiplication. Standalone `microsoft.compute/images` are unaffected.

[^15]: **Data Warehouse (AWS) — EMR cluster states:** `emr:cluster` is filtered to `STARTING`, `BOOTSTRAPPING`, `RUNNING`, and `WAITING`. `list_clusters` with no state filter returns terminated clusters for roughly the trailing two months, and EMR clusters are transient by design — a customer running nightly job clusters would otherwise report hundreds of dead clusters. This mirrors the instance-state filter already applied to `ec2:instance`. `TERMINATING` is excluded on the grounds that the capacity is already being released; flip it into the list if a live run shows meaningful churn at that boundary.

[^16]: **Serverless Container (GCP) — gen2 function overlap:** Cloud Run services that exist only to back a 2nd-gen Cloud Function are excluded from `run.googleapis.com/Service`. Gen2 functions are implemented as Cloud Run services, so without this filter every gen2 function is counted twice — once here and once under Serverless Function. The exclusion keys on the `goog-managed-by=cloudfunctions` label that Cloud Functions applies to the services it provisions. There is no AWS or Azure equivalent to this overlap. **Worth confirming in a live run** that the label appears where expected in Cloud Asset Inventory's resource data; if it does not, the filter silently stops firing and the double-count returns.

[^17]: **VM (Azure) — Resource Graph table selection, and a bug this fixed.** Resource Graph splits resource types across separate tables, and `microsoft.compute/virtualmachinescalesets/virtualmachines` exists **only in the `ComputeResources` table** — it is not in the default `Resources` table. This type was added to the mapping to close the "AKS nodes are invisible on Azure" gap, but because the script queried `Resources`, it silently returned zero and the gap was never actually closed. The VM category now issues two queries: `Resources` for `microsoft.compute/virtualmachines` and `ComputeResources` for the scale set instances. The two are disjoint — Uniform-mode instances (which is what AKS node pools use) appear only in `ComputeResources`, and Flexible-mode instances appear in `Resources` as ordinary `microsoft.compute/virtualmachines` — so this is purely additive with no double-count. **Expect Azure VM counts to rise substantially for AKS-heavy subscriptions relative to any sizing run made before this change.**

[^18]: **VM — virtual desktops are excluded on all CSPs.** AWS WorkSpaces are deliberately *not* counted. This is not a gap: it's a policy decision to keep VDI out of the environment count entirely. Because Azure Virtual Desktop session hosts are ordinary VMs (or scale set instances) in the customer's own subscription, they would otherwise be counted implicitly, so they are excluded explicitly — the VM queries `leftouter`-join `microsoft.desktopvirtualization/hostpools/sessionhosts` from the `DesktopVirtualizationResources` table and drop the rows that match. Resource Graph supports no `leftanti` join flavor, hence the join-then-filter-nulls shape. The exclusion is applied to both the `Resources` and `ComputeResources` VM queries, since host pools can be VMSS-backed. GCP has no first-party VDI offering, so no equivalent exclusion is needed. **Verify in a live run** that session hosts are actually being excluded; if the join does not match, VDI silently starts counting on Azure again.

On GCP, user-managed Vertex AI Workbench VMs are real `compute.googleapis.com/Instance` assets in the customer's project and are already counted with no extra work. **Azure ML compute instances are counted** (2026-09-25, SIZING-SCRIPT OI-29). `microsoft.machinelearningservices/workspaces/computes` is not indexed by Resource Graph (workspaces, batch endpoints, online endpoints and inference pools are, but computes are not). So a space with an app `InService`, `Pending` or `Deleting` counts on this line, and one with no running app counts at the disk weight as `sagemaker:idle-space` ([^26]). **Not counted, and known:** apps that hang off a user profile rather than a space. [^20]: **Data Warehouse (AWS) — serverless.** `redshift-serverless:namespace` and `emr-serverless:application` added; customers fully migrated off provisioned Redshift previously counted zero here. Namespace, not workgroup, is the counted unit for Redshift Serverless: a namespace is the database/storage/identity boundary and the closest analogue to `redshift:cluster`, whereas a workgroup is RPU compute sizing and closer to a SKU — a single logical warehouse with two workgroups counts once. `emr-serverless:application` excludes applications in `TERMINATED` state, consistent with the `emr:cluster` state filter in [^15]; the jobs that run inside an application are ephemeral and are not counted. No Azure or GCP additions are needed: Synapse serverless SQL pools live inside the already-counted workspace, and BigQuery is serverless by nature and already counted at Dataset level.

[^21]: **Bucket Storage (Azure) — containers, not accounts.** Until 2026-09-25 this row counted storage *accounts*, while AWS and GCP count individual buckets, and a single storage account can hold arbitrarily many blob containers. That undercounted Azure relative to the other two CSPs, sometimes by an order of magnitude. Containers are not indexed by Resource Graph. **This footnote used to say that closing the gap needed data-plane calls with `Storage Blob Data Reader`, and would fail behind private endpoints. All three claims were wrong** (corrected 2026-09-25). `Blob Containers - List` is a Storage Resource Provider call on `management.azure.com`. Its permission, `Microsoft.Storage/storageAccounts/blobServices/containers/read`, is a control-plane *Action*, so `Reader` covers it (listing blobs is the DataAction). Microsoft documents that storage firewall rules apply only to data-plane operations. So container counting needs one management call per storage account and **no new permission**. **Containers are now counted in place of accounts** (2026-09-25, SIZING-SCRIPT OI-28), excluding Azure's `$`-prefixed system containers (`$logs`, `$web`). Soft-deleted containers are not listed. **An account with no containers counts as 1**, because it can still hold file shares, queues or tables, and 1 is what it counted before. So switching units never makes an account vanish. An account whose list fails also counts as 1 and trips the `storage_containers_all_listed` canary. Verified live on demo-beta: 4 accounts became 5 containers. It is **not** the same limitation as the ACR undercount in [^5], which genuinely is data-plane.

[^22]: **Managed DB (PaaS) — Redis/Valkey coverage.** Azure `microsoft.cache/redisenterprise` added: `microsoft.cache/redis` covers only the Basic/Standard/Premium tiers, so Enterprise tiers and Azure Managed Redis previously counted zero. GCP `redis.googleapis.com/Cluster` (Memorystore for Redis Cluster, a distinct asset type from single-instance Redis, and the analogue of AWS `elasticache:replication-group`), `memcache.googleapis.com/Instance` (Memorystore for Memcached) and `memorystore.googleapis.com/Instance` (Memorystore for Valkey) added. [^23]: **Managed DB (PaaS) — HA replicas count once, on every CSP.** Ruled 2026-08-14: a managed database counts as one provisioned resource regardless of how many instances back it, because replica count is an HA/scaling knob rather than a distinct workload. **This footnote used to say AWS and Azure already behaved this way. That was only partly true** (corrected 2026-10-26, OI-48): `rds:db` did exclude Aurora cluster members, and Azure HA replicas are not separate resources, but RDS read replicas, cross-region and global secondaries, and Azure geo-replicas and read replicas all counted once per copy until 2026-10-26. **GCP was the first outlier changed:** `sqladmin.googleapis.com/Instance` returns Cloud SQL read replicas as their own assets, so a primary with two read replicas counted 3 where the other two CSPs counted 1. Replicas are now excluded via `instanceType == "READ_REPLICA_INSTANCE"`, falling back to a non-empty `masterInstanceName`. Regional (HA) Cloud SQL needs no handling — the standby is not a separate instance in the API. GCP was also internally inconsistent here, since `alloydb.googleapis.com/Cluster` was already cluster-level. **Verify in a live run:** if Cloud Asset Inventory's RESOURCE content carries neither field, replicas cannot be identified; the filter warns once and counts them rather than failing silently, so the failure mode is a visible over-count rather than a silent one. **AWS had two more outliers, fixed 2026-10-15** (found reviewing the TCS Managed DB breakdown). *DynamoDB global tables:* each replica is a full table in its own region's `ListTables`, so a table replicated to three regions counted 3. Its Config rung is withdrawn until a live account confirms that Config records that field: a filter on a field that is never recorded would keep every member and quietly restore the double count. **Applied to every copy the APIs expose, 2026-10-26 (OI-48),** after the rule was reaffirmed on the Usage Visibility PRD (DATA-5362), so the scripts and the product count the same way. [^24]: **Billable Ratio.** The per-category multiplier that converts a raw resource count into **billable resources**, the single figure a customer is quoted on. Read `N:1` as *N counted resources = 1 billable resource*, so Container Image at `300:1` means 300 images bill as one; `1:1` passes the count through unchanged. The weighted figures across all rows sum to the quoted total.

    **These are a pricing input, not a measurement one.** They are set by the PM team and are not derived from anything the scripts query — the scripts emit raw per-category counts and do not apply the ratio. A ratio is a single multiplier and so **normalises scale, not shape**: it decides how much a category costs, not which customers pay it. Two customers with ten buckets each, one holding 10 TB and one 10 GB, are identical under bucket count and remain identical under any ratio.

[^25]: **Developer.** Like Deployed Agent [^13], a FortiCNAPP billing construct rather than a cloud-native resource type: it represents one developer using the Code Security product. There is no CSP resource type behind it and nothing for the scripts to query on any cloud — **the number is determined by the customer, not discovered by the scripts**, and is entered manually alongside Deployed Agent. Neither category appears in the scripts' stdout table or JSON output.


[^26]: **Stopped instances count once, at the disk weight.** Ruled 2026-09-17. A stopped instance **leaves the VM line**, and **its boot disk is re-admitted to Non-OS Disk**. This is a *re-categorization, not an exclusion* — stopped instances remain in scope, consistent with the ruling that the deliverable is the size of a customer environment and a stopped instance is a distinct provisioned resource, not a wrapper.

    **Why it is required for coherence.** The boot-disk exclusion in [^12] is justified by "the VM line already accounts for it." That justification lapses the moment the VM is not counted, and without re-admission a stopped instance carrying only a root volume would score zero on **both** lines and vanish from the count entirely — while agentless workload scanning still scans it. Each exclusion is individually justified by "captured elsewhere"; together they capture nothing. The rule is therefore conditional: **count a boot disk exactly when its VM is not counted.**

    | | VM line | Non-OS Disk line | Total units |
    |---|---|---|---|
    | Running, 3 data disks | 1 | 3 (boot excluded) | **4** |
    | Stopped, 3 data disks | 0 | 4 (boot re-admitted) | **4** |

    **Unit-preserving, weight-shifting.** The count is identical; only the billing weight changes, from 1:1 to 3:1 ([^24]). That is arguably more accurate: a stopped instance is still scanned agentlessly but runs no agent, so it genuinely consumes less product.

    **Implementation must map power states per CSP, never match strings.** The `--exclude-stopped` flag uses **AWS terminology**, and a naive string match does the *opposite* of what is intended on GCP:

    | CSP | "Stopped" is | Trap |
    |---|---|---|
    | AWS | `stopped` | `terminated` means **destroyed**, not stopped |
    | GCP | `TERMINATED` | The AWS word for destroyed is GCP's word for stopped; deleted instances simply vanish from the API |
    | Azure | `PowerState/stopped` **and** `PowerState/deallocated` | Both read as "stopped" to a human; only `deallocated` releases compute billing |

    This also adds a power-state lookup to the existing disk-to-VM join from `e1cbde7`, which gives the GCP boot-disk fallback a second way to be wrong — a canary target rather than a silent one.

    **Decided on the user's behalf, vetoable:** transitional states (`stopping`, `shutting-down`, `STOPPING`) count as **still-a-VM**, since the instance remains allocated until it reaches a settled stopped state and treating them otherwise makes the count flap during normal operations. **One exception, ruled 2026-10-26 (OI-50): GCP `STOPPING` counts as stopped.** A GCP-side bug over-reports instances in that state, which confused customers, so the vCPU model ([vCPU overview](https://docs.fortinet.com/document/forticnapp/latest/administration-guide/857349/subscriptions#vcpu-overview)) excludes it on GCP alone, and sizing and Usage Visibility follow. It applies to GCP and to `STOPPING` only: `PENDING_STOP`, `SUSPENDING` and the AWS and Azure transitional states still count as VMs; Azure `PowerState/stopped` and `PowerState/deallocated` are **both** treated as stopped, since under a resource count — as opposed to the old vCPU consumption model — what matters is that the instance is not running and its disks persist.

    **Implemented 2026-09-17** in `d52336d` (AWS), `043029f` (GCP) and `cd47373` (Azure). Three things the implementation settled or exposed:

    - **GCP has no `STOPPED` status at all.** Confirmed against the Compute Engine instance-lifecycle reference: the statuses are `PENDING`, `PROVISIONING`, `STAGING`, `RUNNING`, `PENDING_STOP`, `STOPPING`, `TERMINATED`, `REPAIRING`, `SUSPENDING`, `SUSPENDED`. A stopped instance reads `TERMINATED`, exactly as the trap table above warns. **`SUSPENDED` is also treated as stopped** — decided on the user's behalf and vetoable — by the same reasoning applied to Azure's two states: the machine is not running and its disks persist. Both the AWS and GCP filters test a *stopped* set rather than a counted-states allow-list, so a state a CSP adds later counts as a VM (a visible over-count) rather than vanishing from both lines (a silent under-count).
    - **Azure needed a new disk-to-VM join**, because it never had one — OS disks were excluded on the disk's own `properties.osType`. The join is narrow: `managedBy` must resolve to a plain `microsoft.compute/virtualmachines` row in a stopped state. Scale-set-owned OS disks deliberately do not match, since that instance is already counted via `ComputeResources` and re-admitting would double-count every AKS node's OS disk. **Azure scale-set instance power state is unverified** — no published Resource Graph sample covers it — so an unreadable power state leaves the VM counted, making the worst case on that table today's behaviour rather than a silent drop. Canary target.
    - **Exposed, not fixed: Azure excludes unattached OS disks** while AWS and GCP both count a detached former boot disk as ordinary provisioned storage ("unattached volumes are still counted", [^12]). That divergence predates this ruling and sits outside its scope, so it is recorded here rather than changed. Also known and bounded: a *stopped* AVD session host's OS disk is now re-admitted even though VDI is excluded from the VM line as policy.

    **Extended 2026-09-17 — hibernated instances count as stopped, and Azure's unattached OS disks are now counted.** Both ruled by the user (PM) after the implementation pass exposed them.

    - **Hibernation counts as stopped, and all three CSPs were already consistent.** A hibernated machine is not running and its disks persist, which is exactly the test this footnote applies. Azure documents hibernation as storing RAM into the OS disk and then *deallocating* the VM, billed "just like a stop (deallocated) state", so `PowerState/deallocated` already catches it. AWS has no hibernated value in `InstanceStateName` at all, so an AWS hibernated instance reports `stopped`. GCP's suspend-to-disk reports `SUSPENDED`, already treated as stopped above. No cloud needed a new rule — the ruling confirms the existing one.
    - **Azure's unattached OS disks are now counted**, closing the divergence recorded below as exposed-not-fixed. It was an oversight, not a platform limitation: `managedBy` is documented as "a relative URI containing the ID of the VM that has the disk attached" and is absent when nothing is attached, and `properties.diskState` carries an explicit `Unattached` value. **Reaffirmed 2026-10-26 (OI-51)** for Usage Visibility: any unattached disk is a Non-OS Disk on every cloud, including a boot disk left behind when its VM was deleted. AWS has no way to tell such a disk from a data disk, so counting every unattached disk is the rule that is the same on all three.
    - **`DiskState` turned out to state the relationship directly.** The documented enum includes `Reserved` ("attached to a stopped-deallocated VM"), `Frozen` ("attached to a VM which is in hibernated state") and `ActiveSASFrozen`. Azure reports on the disk what the power-state join reconstructs through `managedBy`. It is used **as a union with** that join rather than a replacement: `Reserved` is documented specifically as stop-*deallocated*, so a VM merely stopped while still allocated keeps an `Attached` disk and is only caught by the join.
    - **Scale-set-owned disks are excluded from the `DiskState` route too.** A Uniform-mode scale-set instance is counted through `ComputeResources`, where power state is unverified, so re-admitting its OS disk on `Reserved` would double-count a stopped AKS node against a VM row that still counts it as running.
    - **This yields a free cross-check** on the part of the Azure implementation that cannot be verified without a tenant: if OS disks report `Reserved` or `Frozen` while the power-state test found no stopped VMs, that test is missing a state. Wired as a canary.

    **Managed DB does not inherit this rule** and needs no equivalent: the mapping counts DB instances and clusters rather than their storage, so a stopped database has no second line to land on. It is handled instead by skipping the Cost Explorer rung for that row entirely (ruled 2026-09-17), leaving Managed DB on state instruments that see stopped resources natively. A stopped RDS instance also keeps its full configuration surface — endpoint, public IP, security group, parameter and option groups — and FortiCNAPP's coverage of managed databases is configuration/compliance policy evaluation, which is state-independent, so there is no basis for weighting it lower.

    **Applied to SageMaker on 2026-09-25 (OI-4).** A notebook instance that is `Stopped` or `Failed`, and a Studio space with no running app, keep their ML storage volume but run no instance. They move to Non-OS Disk as `sagemaker:stopped-notebook-instance` and `sagemaker:idle-space`. Until then every notebook state was counted on the VM line, a default taken from precedent in August, before this ruling existed. The environment is counted as one unit either way: running, it counts once as a VM; stopped, once as a disk. Its storage volume lives in an AWS-managed account where no `ec2:volume` sees it, so there is no boot-disk join to keep in step. The notebook type leaves the AWS Config rung for the same reason. With its running and stopped halves on different lines, a Config count would need the notebook's status from the configuration item, and that has not been verified.

[^28]: **Data Warehouse — a cluster counts here and its machines count as VMs.** Ruled 2026-10-26 (OI-49), on a question from the Usage Visibility PRD, keeping what the scripts already did. This is not a double count: the cluster is the warehouse service and the machines are hosts the product protects.
